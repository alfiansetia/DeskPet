# DeskPet — Product Requirements Document (PRD)

> **Status:** Draft v1.0  
> **Product type:** Open-source desktop companion / personal productivity assistant  
> **Platforms:** Windows 10/11 and macOS  
> **Primary stack:** Rust, Tauri 2, React, TypeScript, SQLite  
> **Product principle:** Local-first, privacy-first, permission-based

---

## 1. Product Summary

DeskPet is an open-source desktop companion for Windows and macOS. An animated character lives on the user's desktop and provides a friendly interface for reminders, tasks, notes, text-to-speech, natural-language commands, optional AI, calendar/email integrations, and user-approved automations.

DeskPet takes inspiration from classic desktop companions such as Bonzi Buddy, but is designed around modern privacy, security, accessibility, and user control.

### Product vision

Build a useful desktop companion that feels alive without spying on the user, requiring a cloud account, or surrendering control of the computer.

### Product principles

1. **Local-first:** Core features work without an account or internet connection.
2. **Privacy-first:** No telemetry by default; no hidden collection of screenshots, keystrokes, clipboard contents, or application data.
3. **Permission-based:** External and sensitive actions require explicit, understandable authorization.
4. **Cross-platform:** Shared application logic for Windows and macOS, with native adapters where needed.
5. **Extensible:** New capabilities can be added through a controlled action/plugin API.
6. **Transparent:** Clearly show what the app is doing, which integrations are connected, and what data leaves the device.
7. **Accessible:** Keyboard navigation, reduced motion, quiet mode, and adjustable animation/sound.

## 2. Goals and Non-Goals

### Goals

- Provide an animated desktop character that can be moved, hidden, clicked, and customized.
- Support reminders, alarms, recurring schedules, snooze, and native notifications.
- Provide local to-do lists and notes.
- Speak through native operating-system text-to-speech where available.
- Parse natural-language requests into validated, structured actions.
- Support optional local AI or external AI providers.
- Support calendar and email integrations through provider adapters.
- Allow users to create automations that are previewed and authorized.
- Keep user data local unless the user explicitly enables an external integration.
- Package, test, and release for Windows and macOS.

### Non-goals for the initial release

- A general-purpose autonomous agent with unrestricted computer access.
- Arbitrary shell execution generated by AI.
- Silent monitoring of user activity.
- Cloud synchronization or mandatory accounts.
- Sending email or modifying external data without user confirmation.
- Dynamic execution of untrusted third-party plugin code in the main process.
- Guaranteed alarm delivery while the computer is powered off.

## 5. Functional Requirements

### 5.1 Desktop Character

**Description:** An animated character displayed in a transparent desktop window.

#### Requirements

- The character can be shown, hidden, dragged, and repositioned.
- The character window can be configured as always-on-top.
- The character supports multiple animation states.
- The user can select available character themes and animation sets.
- The app supports multiple monitors and display scaling.
- The user can disable animations or enable reduced-motion mode.
- The user can mute speech and sound effects independently.
- The user can choose whether the character receives mouse clicks or lets clicks pass through when idle, subject to platform support.
- The app must not capture mouse or keyboard input globally unless a specific, user-enabled feature requires it.

#### Initial animation states

- `idle`
- `walk`
- `dragged`
- `react`
- `sleep`
- `speak`
- `reminder`
- `attention`

#### Acceptance criteria

- Character state changes do not require reloading the app.
- Dragging the character does not accidentally trigger clicks on the UI behind it.
- Hide/show works from the tray/menu bar and keyboard shortcut.
- The app remains usable if an animation asset is missing or invalid.
- Window behavior is tested on both Windows and macOS.

### 5.2 Reminders, Alarms, and Notifications

#### Requirements

- Create one-time and recurring reminders.
- Edit, complete, dismiss, and snooze reminders.
- Support a title, optional description, due time, timezone, and recurrence.
- Deliver native notifications when the app is running.
- Restore pending reminders after app restart.
- Handle missed reminders after sleep, shutdown, or application downtime.
- Prevent duplicate notifications for the same occurrence.
- Allow notification sound, speech, and character animation to be configured independently.
- Provide a quiet-hours setting.
- Show a clear fallback message if notification permissions are denied.

#### Scheduling rules

- Store absolute timestamps in UTC.
- Store the IANA timezone used to interpret local recurring schedules.
- Define and test daylight-saving-time behavior.
- Use the database as the source of truth; do not rely solely on frontend timers.
- Do not promise delivery while the computer is powered off. Native OS scheduling can be evaluated as a later enhancement.

#### Acceptance criteria

- A pending reminder remains stored after restarting DeskPet.
- A recurring reminder generates no duplicate occurrence.
- Snooze creates a new due time without deleting the original reminder definition.
- Invalid timezone or recurrence values are rejected safely.
- The UI clearly indicates notification permission problems.

### 5.3 To-Do List

#### Requirements

- Create, edit, complete, reopen, search, and delete tasks.
- Support priority, due date, optional description, and labels.
- Link a task to a reminder.
- Filter tasks by status, priority, and due date.
- Offer undo or a trash mechanism for accidental deletion.
- Store all task data locally.

#### Initial statuses

- `open`
- `in_progress`
- `completed`

### 5.4 Notes

#### Requirements

- Create, edit, search, and delete text notes.
- Autosave with visible save status.
- Support soft delete and restore.
- Export/import notes through an explicit user action.
- Never include note contents in logs by default.
- Do not send notes to an AI provider unless the user explicitly submits them.

### 5.5 Text-to-Speech (TTS)

#### Requirements

- Use native OS speech APIs through a provider abstraction.
- Provide voice, rate, volume, mute, and test-speech controls where supported.
- Queue speech so simultaneous reminders do not overlap unexpectedly.
- Allow users to stop current speech.
- Do not speak note contents, email bodies, or other sensitive content automatically.
- Provide visual notifications if speech is unavailable.

#### Suggested interface

```rust
pub trait SpeechProvider {
    fn available_voices(&self) -> Result<Vec<VoiceInfo>, SpeechError>;
    fn speak(&self, text: &str, options: SpeechOptions) -> Result<(), SpeechError>;
    fn stop(&self) -> Result<(), SpeechError>;
}
```

The exact implementation may need asynchronous methods or platform-specific wrappers.

### 5.6 Natural-Language Commands and AI

#### Example requests

- “Remind me to deploy at 4 PM.”
- “Add buy groceries to my to-do list.”
- “Start a 25-minute focus timer.”
- “What tasks are due today?”
- “Create a draft email to the team about tomorrow’s meeting.”

#### Requirements

- Parse natural-language input into a typed action request.
- Support deterministic local parsing for common reminders and timers.
- Allow optional AI providers, including a local model or external API.
- Do not require AI for reminders, notes, or tasks.
- Validate every action in Rust before execution.
- Resolve ambiguous dates and times by asking the user.
- Clearly indicate whether a request will be processed locally or sent to an external provider.
- Never let AI directly access SQLite, OS APIs, credentials, or shell execution.
- Treat email, web pages, documents, plugin results, and model outputs as untrusted input.

#### Action request example

```ts
type ActionRequest =
  | {
      type: "reminder.create";
      title: string;
      dueAt: string;
      timezone: string;
    }
  | {
      type: "todo.create";
      title: string;
      dueAt?: string;
    }
  | {
      type: "note.create";
      title: string;
      content: string;
    }
  | {
      type: "timer.start";
      durationSeconds: number;
    };
```

This TypeScript union is an illustrative contract. Rust-side types and validation must be authoritative.

### 5.7 Action Registry and Permission Engine

#### Requirements

- Maintain a registry of explicitly supported actions.
- Every action has an identifier, input schema, permission requirements, and risk classification.
- Reject unknown actions and invalid payloads.
- Apply allowlists; do not execute arbitrary commands supplied by AI.
- Display a preview before external or sensitive actions.
- Record minimal local audit metadata without logging private content.
- Provide a central page for reviewing and revoking permissions.

#### Default policy

| Action class | Example | Default behavior |
|---|---|---|
| Read-only local | List tasks | Execute if feature is enabled |
| Local write | Create a task or note | Follow user settings; offer undo |
| Scheduled | Create a reminder | Validate and confirm ambiguous values |
| External read | Search email or list calendar events | Require connected provider and granted scope |
| External write | Create calendar event or email draft | Preview and confirm |
| High-risk | Send email, delete external data, run shell | Explicit confirmation; unavailable unless deliberately implemented |

### 5.8 Plugin System

#### Initial design

Start with statically registered, first-party Rust modules. Do not load arbitrary executable code in the main process.

Each plugin should define:

- Stable plugin ID and version.
- Compatible DeskPet API version.
- Actions it exposes.
- Permissions it requests.
- Input/output schemas.
- Error handling and timeout behavior.
- Data-handling disclosure.
- Tests and documentation.

#### Example manifest

```json
{
  "id": "calendar.google",
  "name": "Google Calendar",
  "apiVersion": 1,
  "permissions": [
    "calendar.events.read",
    "calendar.events.create"
  ],
  "actions": [
    "calendar.list_events",
    "calendar.create_event"
  ]
}
```

Dynamic third-party plugins are a later milestone. Before enabling them, design process isolation, a capability model, signing or trust policies, and resource limits.

### 5.9 Calendar Integration

#### Initial provider

Google Calendar, through OAuth 2.0 and the official API.

#### Initial capabilities

- Connect and disconnect an account.
- List events in a selected date range.
- Create a calendar event after showing a preview and obtaining confirmation.
- Display provider connection state and granted scopes.
- Revoke access and delete local tokens when disconnected.

Use the narrowest available OAuth scopes. Provider verification may be required before public distribution.

### 5.10 Email Integration

#### Initial provider

Gmail, through OAuth 2.0 and the official API.

#### Initial capabilities

- Search or list messages using limited scopes.
- Display metadata needed for the feature.
- Create a draft email.
- Require explicit review before sending.
- Never upload email content to AI without explicit consent.
- Keep access tokens in OS credential storage, not SQLite as plaintext.

Sending email should not be enabled by default in early releases.

### 5.11 User-Approved Automations

#### Examples

- Every weekday at 9 AM, show today’s tasks.
- When a reminder is due, show a notification and offer to speak it.
- Every Friday, create a review task.
- Before a calendar event, show a reminder 10 minutes earlier.

#### Requirements

- Automations use a constrained trigger/action model.
- Show a readable summary before saving an automation.
- Show the actions and permissions required.
- Allow pause, edit, run-once, and delete.
- Log the execution result without sensitive payloads.
- Require fresh confirmation for external writes unless the user explicitly enables a narrowly scoped recurring rule.
- Provide loop prevention, rate limits, and failure handling.

## 7. Technical Architecture

### Stack

| Layer | Technology | Responsibility |
|---|---|---|
| Desktop runtime | Rust + Tauri 2 | OS integration, windows, lifecycle, commands |
| UI | React + TypeScript + Vite | Panels, settings, assistant, forms |
| Animation | Sprite sheets + Canvas/CSS | Character states and transitions |
| Database | SQLite through Rust | Local persistent data |
| Scheduler | Rust service + database | Reminder occurrences and scheduled jobs |
| Notifications | Tauri plugin / OS adapter | Native notifications |
| TTS | Native Windows/macOS adapters | Local speech |
| AI | Provider abstraction | Local model or external API |
| Integrations | OAuth 2.0 provider adapters | Calendar and email |
| Testing | Rust tests, Vitest, Playwright | Unit, UI, integration, regression |

### Architecture flow

```text
React UI
  |
  | Tauri invoke/events
  v
Rust Application Core
  |
  +-- Command Router
  +-- Input Validation
  +-- Permission / Policy Engine
  +-- Action Registry
  +-- Reminder Scheduler
  +-- Database Repository
  +-- TTS Provider
  +-- Notification Provider
  +-- AI Provider Adapter
  +-- Calendar / Email Adapters
  |
  v
SQLite + OS APIs + explicitly enabled external providers
```

### Architecture rules

- Rust is authoritative for persistence, validation, permissions, and execution.
- React must not connect directly to SQLite or external provider credentials.
- Use Tauri capabilities and narrowly scoped permissions.
- Keep platform-specific behavior behind adapters.
- Treat external content and AI output as untrusted.
- Do not put secrets in frontend code or environment variables bundled into the client.
- Keep core features functional with all network integrations disabled.

## 8. Database Design

The following is an initial schema sketch. Production migrations must add indexes, constraints, migration versioning, and tested rollback/recovery behavior.

```sql
CREATE TABLE reminders (
    id TEXT PRIMARY KEY,
    title TEXT NOT NULL,
    body TEXT,
    due_at TEXT NOT NULL,
    timezone TEXT NOT NULL,
    recurrence_rule TEXT,
    status TEXT NOT NULL DEFAULT 'active',
    snooze_until TEXT,
    last_triggered_at TEXT,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);

CREATE TABLE todos (
    id TEXT PRIMARY KEY,
    title TEXT NOT NULL,
    description TEXT,
    status TEXT NOT NULL DEFAULT 'open',
    priority INTEGER NOT NULL DEFAULT 0,
    due_at TEXT,
    completed_at TEXT,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);

CREATE TABLE notes (
    id TEXT PRIMARY KEY,
    title TEXT NOT NULL DEFAULT '',
    content TEXT NOT NULL DEFAULT '',
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    deleted_at TEXT
);

CREATE TABLE integrations (
    id TEXT PRIMARY KEY,
    provider TEXT NOT NULL,
    account_label TEXT,
    permissions_json TEXT NOT NULL DEFAULT '[]',
    connected_at TEXT NOT NULL,
    revoked_at TEXT
);

CREATE TABLE scheduled_jobs (
    id TEXT PRIMARY KEY,
    action_id TEXT NOT NULL,
    payload_json TEXT NOT NULL,
    run_at TEXT NOT NULL,
    status TEXT NOT NULL DEFAULT 'pending',
    attempts INTEGER NOT NULL DEFAULT 0,
    created_at TEXT NOT NULL
);

CREATE TABLE action_audit (
    id TEXT PRIMARY KEY,
    action_id TEXT NOT NULL,
    source TEXT NOT NULL,
    status TEXT NOT NULL,
    confirmation_required INTEGER NOT NULL DEFAULT 0,
    created_at TEXT NOT NULL
);
```

### Database rules

- Store absolute timestamps in UTC and recurring schedule timezone separately.
- Use transactions for multi-table updates.
- Add indexes for due reminders and task status/deadline.
- Never store OAuth secrets as plaintext in SQLite.
- Avoid logging note bodies, email content, prompts, or other sensitive content.
- Provide explicit local backup and restore.
- Test migrations against older released database versions.

## 9. Security and Privacy Requirements

### Must-have safeguards

- No telemetry by default.
- No hidden screenshots, keylogging, clipboard monitoring, or application-content collection.
- No network requirement for reminders, tasks, notes, or basic character behavior.
- Explicit opt-in for external AI and provider integrations.
- Minimal OAuth scopes.
- Tokens stored using OS credential storage where feasible.
- Permission checks happen in Rust, not only in the UI.
- AI cannot execute arbitrary shell commands.
- Unknown actions and malformed payloads are rejected.
- External writes show a preview and require confirmation.
- Users can disconnect integrations and revoke access.
- Logs contain minimal metadata and never private content by default.
- Dependency auditing, vulnerability reporting, and release signing are part of release preparation.

### AI safety

- AI produces structured action requests only.
- Rust validates action type, fields, ranges, permissions, and risk level.
- Treat prompt injection in emails, webpages, notes, documents, and plugin output as untrusted content.
- Ask for clarification when dates, recipients, or action intent are ambiguous.
- Never send private content to a cloud provider without an explicit user action and clear disclosure.

- Friendly, modern desktop companion.

The initial public beta is ready when:

1. Desktop pet behavior works reliably on Windows and macOS.
2. Local reminders, tasks, and notes are stable.
3. Notifications and TTS degrade gracefully when unavailable.
4. Privacy defaults are documented and tested.

## 17. Guidance for an AI Coding Agent

Use this PRD as the product source of truth.

### Working rules

1. Start by inspecting the repository and summarizing its current state.
2. Implement in small, testable milestones; do not generate the entire application in one pass.
3. Create or update `docs/architecture.md` before major architectural changes.
4. Keep Rust authoritative for data, permissions, and actions.
5. Keep the core usable without AI or internet.
6. Never implement arbitrary shell execution from AI output.
7. Never store secrets in frontend code or plaintext SQLite fields.
8. Add tests for each feature and run them before moving to the next milestone.
9. Document platform-specific limitations instead of silently pretending behavior is identical.
10. Ask before introducing a major dependency, external service, or change to the privacy model.
11. Do not claim a feature is complete until it has been implemented and tested.
12. Prefer secure, boring, maintainable implementations over clever abstractions.

### First implementation task

Implement **P1 — Foundation** only:

- Inspect the repository.
- Initialize Tauri 2 + Rust + React + TypeScript if not already present.
- Create a transparent desktop pet window.
- Implement a placeholder character and basic idle animation.
- Add drag, hide/show, and tray/menu bar controls where supported.
- Create the initial SQLite migration setup.
